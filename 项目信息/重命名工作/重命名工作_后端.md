## 重命名接口设计方案

### 1. 接口概述
为线上文件夹模块（类似云盘）增加重命名功能，允许用户对个人存储的文件或文件夹进行重命名操作。接口需遵循 RESTful 风格，基于现有技术栈（Spring MVC + MyBatis）实现。

### 2. 功能需求
- 用户登录后，可对自己拥有的文件或文件夹进行重命名。
- 重命名时检查新名称是否合法（长度、字符限制等）。
- 同一父目录下不允许出现同名文件/文件夹（名称 + 路径唯一）。
- 若重命名的是文件夹，需考虑其内部所有子项路径的同步更新（递归更新 `path` 字段）。
- 操作需保证数据一致性（使用数据库事务）。
- 返回明确的成功/失败信息。

### 3. 接口定义

#### 3.1 请求 URL
- **URL**: `/file`
- **方法**: `Patch` 

#### 3.2 请求参数
建议采用 JSON 格式传递参数：

| 字段名   | 类型   | 必填 | 说明                           |
|----------|--------|------|------------------------------|
| id       | Long   | 是   | 待重命名的文件/文件夹的 ID     |
| newName  | String | 是   | 新名称（不能为空，不能含路径分隔符） |

**示例**：
```json
{
    "id": 123,
    "newName": "新文件名.pdf"
}
```

#### 3.3 响应格式

**成功响应**：
```json
{
    "code": 200,
    "message": "重命名成功",
    "data": {
        "id": 123,
        "oldName": "旧文件名.pdf",
        "newName": "新文件名.pdf"
    }
}
```

**失败响应**（示例）：
```json
{
    "code": 400,
    "message": "新名称不能为空",
    "data": null
}
```

| 字段名  | 类型   | 说明                       |
|---------|--------|----------------------------|
| code    | int    | 状态码（200成功，其他失败）|
| message | String | 提示信息                   |
| data    | Object | 可选，返回额外数据         |

### 4. 业务逻辑设计

#### 4.1 权限校验
- 从当前会话（如 HttpSession）中获取登录用户 ID（`userId`）。
- 根据请求的 `id` 查询 `folder` 表，确认该记录存在且 `user_id` 等于当前用户 ID，否则返回无权限错误。

#### 4.2 名称合法性校验
- 新名称不能为空，长度限制（例如 1~255 字符）。
- 不能包含路径分隔符 `/` 或 `\`（根据系统要求，README中建议统一使用 `/`，因此新名称中不应包含 `/`）。
- 可进一步限制特殊字符（如 `< > : " | ? *`），根据需求决定。

#### 4.3 冲突检查
- 获取原记录的信息：`path`（父路径，例如 `/docs`）和原名称。
- 构造新路径：`newPath = 原父路径 + "/" + newName`（注意处理根目录情况）。
- 查询同一用户下是否存在 `path = newPath` 且 `name = newName` 的记录（实际上 path 已包含完整路径，但 name 字段冗余存储，需同时校验两者或仅校验 path 唯一性）。建议以 `path` 字段作为唯一标识，同一父目录下不能有同名对象。
- 若存在冲突，返回错误。

#### 4.4 执行重命名
- **文件（type = 'file'）**：直接更新该记录的 `name` 和 `path`（路径更新为 `newPath`）。
- **文件夹（type = 'folder'）**：
  - 更新当前文件夹记录的 `name` 和 `path`。
  - 递归更新其所有子项（包括文件和子文件夹）的 `path`：将原路径前缀替换为新路径前缀。
  - 例如：原文件夹路径 `/a/b` 重命名为 `/a/c`，则子项路径 `/a/b/file.txt` 应更新为 `/a/c/file.txt`。
  - 实现方式：执行 SQL `UPDATE folder SET path = REPLACE(path, 旧路径, 新路径) WHERE path LIKE 旧路径 || '/%'`（注意数据库函数兼容性，MySQL 可使用 `CONCAT` 和 `REPLACE`）。
  - 注意只更新属于该用户且路径以旧路径开头的记录，避免误改其他用户数据（通过 `user_id` 过滤）。

#### 4.5 事务控制
- 上述更新操作需在事务中执行，确保原子性。
- 使用 Spring `@Transactional` 注解。

#### 4.6 特殊场景处理
- **根目录**：若重命名的是用户根目录（例如 `path = '/'`），需特殊处理，但通常不允许重命名根目录。可限制 `path` 不为 `/`。
- **空文件夹**：无论空与否均可重命名，递归更新逻辑会自动处理。
- **并发冲突**：考虑使用乐观锁或悲观锁？简单场景下可不处理，若需增强可使用版本号或行锁。

### 5. 数据库操作（MyBatis Mapper 设计）

需要提供以下 Mapper 方法：

1. **根据 ID 查询记录**（用于权限和原信息获取）
   ```java
   Folder selectByIdAndUserId(@Param("id") Long id, @Param("userId") Long userId);
   ```

2. **检查是否存在同名冲突**
   ```java
   int countByPathAndUserId(@Param("path") String path, @Param("userId") Long userId);
   ```

3. **更新单个记录的名称和路径**
   ```java
   int updateNameAndPath(Folder folder);
   ```

4. **递归更新子文件夹路径**（批量更新）
   ```java
   int updateChildrenPath(@Param("oldPath") String oldPath, 
                          @Param("newPath") String newPath, 
                          @Param("userId") Long userId);
   ```

### 6. 异常处理
- 使用 Spring MVC 全局异常处理器（`@ControllerAdvice`）统一返回错误信息。
- 自定义业务异常（如 `PermissionDeniedException`、`ConflictException`），便于区分错误类型。

### 7. 测试方案

#### 7.1 单元测试
- 使用 JUnit + Mockito 对 Service 层进行测试，模拟 Mapper 行为。
- 覆盖场景：
  - 正常重命名文件
  - 正常重命名空文件夹
  - 正常重命名非空文件夹（验证子项路径更新）
  - 权限不足（id 不属于当前用户）
  - 新名称为空或超长
  - 新名称含非法字符
  - 同一目录下重名冲突
  - 目标文件/文件夹不存在
  - 并发更新测试（可选）

#### 7.2 集成测试
- 使用 Spring Test 模块 + 内存数据库（如 H2）模拟真实环境。
- 测试 Controller 层，通过 `MockMvc` 发送 HTTP 请求验证响应。
- 准备测试数据（如插入几条 folder 记录），执行重命名后断言数据库状态。

#### 7.3 手动测试（Postman）
- 模拟真实用户登录（需先实现登录接口或使用测试 Token）。
- 构造不同请求体，检查返回码和数据库变化。
- 验证文件夹递归更新是否正确。

#### 7.4 测试用例示例

| 用例编号 | 描述                         | 前置条件                                 | 输入                                          | 预期结果                                     |
|----------|------------------------------|------------------------------------------|-----------------------------------------------|----------------------------------------------|
| TC01     | 重命名文件成功               | 存在文件 id=1，用户 A 拥有，路径 /docs/a.txt | id=1, newName="b.txt"                        | 返回成功，数据库 name 改为 b.txt，path 改为 /docs/b.txt |
| TC02     | 重命名文件夹成功（非空）     | 存在文件夹 id=2，路径 /folder，下有子文件 id=3，路径 /folder/file.txt | id=2, newName="newfolder"                     | 文件夹 name 改为 newfolder，path 改为 /newfolder；子文件 path 更新为 /newfolder/file.txt |
| TC03     | 权限不足                     | 文件 id=1 属于用户 A，但当前用户为 B     | id=1, newName="x"                             | 返回 403 或自定义错误码，无数据变更            |
| TC04     | 重名冲突                     | 目录 /docs 下已存在文件 b.txt             | 重命名 a.txt 为 b.txt                         | 返回冲突错误，无数据变更                       |
| TC05     | 新名称含非法字符             | 任意文件                                 | newName="a/b.txt"                             | 返回参数校验错误                              |
| TC06     | 重命名根目录（若不允许）     | 存在用户根目录记录 path="/"               | id=根目录ID, newName="newroot"                 | 返回业务错误（如不可操作根目录）              |

### 8. 注意事项
- 数据库中的 `path` 字段需建立索引（尤其是用于 `LIKE` 查询的列），以提升递归更新性能。
- 若文件数量巨大，递归更新可能耗时，可考虑异步处理或分批更新，但简单场景下事务内直接更新即可。
- 确保 `newName` 在存储前进行 HTML 转义（防止 XSS），但一般后端无需处理，前端负责展示转义。

### 9. 后续扩展
- 后续可支持批量重命名（如多选后统一改名）或重命名时自动处理扩展名（如仅修改主文件名）。
- 可增加操作日志记录，记录谁在何时重命名了什么文件。
